# 首跑启动器三大难题排查纪要（里程碑 v2026.08.01.1423）

> 背景：打包成一键 EXE 后，「首次运行」（在下载目录双击便携版本号 exe）必须同时达成三个目标：
> ① 显示启动器界面　② 删除自身（便携 exe）　③ 托盘退出时清理所有派生服务进程。
> 三者相互独立又相互牵制，从 v1507 到 v1423 历经约 20 个发布版本才彻底闭环。本文记录根因、弯路与最终方案，避免后人再踩。

---

## 一、难题 1：首跑「窗口 visible=True、但用户看不到」

### 根因（Windows 前台锁）
首跑由 `supervisor` 用 `subprocess.Popen` 拉起 `entry` 进程，再 `os._exit(0)`。
**Popen 拉起的子进程不继承前台权限**。entry 显示主窗口时 `activateWindow()`→`SetForegroundWindow`
被 Windows 前台锁**静默拒绝** → 窗口 `isVisible()=True`（Qt 确实 show 了）但停在后台被其他窗口盖住 → 用户只看到托盘。

而「二次双击 entry（Explorer 启动）」和「开发模式（终端 `python main.py`）」自带前台权限，故正常。
这就是用户观察到的经典现象：**第一次不行、第二次/开发就行**。

### 💡 决定性反例（定位关键）
启动屏子进程 `BrandedSplash` 同为 Popen spawn 出来，却能正常显示——正因它用了
`WindowStaysOnTopHint`（置顶窗口）。**置顶窗口无视前台锁，必定可见**。这也解释了为什么
当年 f7d9105 用同款 spawn 能首跑显示。

### ❌ 走过的弯路
- `AllowSetForegroundWindow(child_pid)` + `AttachThreadInput + SetForegroundWindow` 这套
  「前台锁 hack」（v0722 / v0901）—— **在用户真机上无效**（hack 在显示后 ~15s 才调用、前台权早已过期）。
- 误判几何 `(680,232)` 为「屏外越界」——其实它是主屏 2560×1440 居中 1200×988 的**正确结果**。

### ✅ 根治（v1412，当前权威）
主窗口显示时先 `setWindowFlags(... | WindowStaysOnTopHint)` **短暂置顶**保证「一定可见」，
`QTimer.singleShot(2000, _drop_topmost)` 2 秒后撤掉标志恢复普通窗口（避免长期盖住用户其他窗口）。
这是启动屏自身就在用的、被证明可靠的同源机制，彻底抛弃不可靠的前台锁 hack。

## 二、难题 2：删除自身（便携 exe）

### 根因
要在「入口进程（entry）」里删除「便携版本号 exe（自身）」。删除时机必须是「打开就删」，
且无需管理员权限、不触发杀软。

### ❌ 走过的弯路
- `MoveFileEx(MOVEFILE_DELAY_UNTIL_REBOOT)` —— 需写注册表、非管理员静默失败。
- `self-delete-helper`「等主进程退出才删」 —— app 运行期进程不退，永远删不掉；且用户要的是「打开就删」。
- 把 `already` 分支条件复杂化（「仅当 ver/ 中无新版时才删」）—— 正常路径直接 return，**永不删**。
- 运行中 rename exe 触发杀软原生层杀进程 → 闪退。

### ✅ 根治（恢复 git `f7d9105` proven 机制）
首跑部署后：`os.link(exe, entry_exe)`（失败回退 copy）+ `shutil.copy2(exe, ver_exe)` +
`subprocess.Popen([entry_exe, "--cleanup=" + exe])` + `os._exit(0)`。
entry 在 `already` 分支**无条件** `os.remove(cleanup_target)` 立即删便携 exe（无需管理员、不触发杀软）。
配套 `.cleanup_pending` 兜底：若 entry 首次被杀软拦截未能删，下次启动再删。

## 三、难题 3：托盘退出后进程残留

### 根因
- 退出清理用脆弱的**关键字扫描**：`psutil` 仅匹配 cmdline 含 `acestep`/`qinglong`，
  而前端跑在 `ace-step-ui/` 目录（带连字符），`acestep` 子串根本不匹配 → **前端 vite 永远漏杀**。
- `ServiceProcess.terminate()` 只 `terminate()` **powershell 父进程**，其拉起的 node/python
  子进程（孙进程）不会被 SIGTERM 连带杀死 → 残留。

### ✅ 根治（v0447）
改用**递归进程树精确清理**：遍历 `psutil.Process(os.getpid()).children()`，
对名字 ∈ {python, node, powershell, pwsh} 的服务型直接子进程，先优雅 terminate 整棵子孙树、
超时 3s 再强杀。`ServiceProcess.terminate()` 与 `api_process` 退出也走同一棵树清理。
**只按进程归属杀服务型进程，绝误杀本启动器或升级时拉起的新版 exe**（其名非上述几类），自更新不受影响。

## 四、最终首跑架构闭环（v1423）

```
便携版本号 exe 双击
  └─ supervisor（Explorer 拉起，带前台权）
       ├─ _kill_old_instances()        按品牌前缀杀旧进程
       ├─ _self_relocate() 首跑分支     建 云集智能音乐创意台/（app/data/ver/python_embeded/temp）+ version.txt
       │                              os.link(exe→入口) + copy2(exe→ver/)
       ├─ Popen([入口, "--cleanup=" + exe]) + os._exit(0)   ← 分离式拉起 entry（删除靠它）
       └─ （entry 进程，already 分支）
            ├─ _archive_to_ver()        把便携 exe 复制进 ver/（幂等）
            ├─ MainWindow 置顶显示 2s    ← 显示靠短暂置顶，无视前台锁
            └─ os.remove(cleanup_target) ← 立即删便携 exe（打开就删）
```

删除（靠独立 entry 进程）与显示（靠置顶窗口）两难已解，互不冲突。

## 五、启动追踪日志策略（v1423 调整）

- `_launch_trace`（launcher.py + main.py）**默认仅写 `%TEMP%/yunji_launch_trace.log`**，
  不污染部署/下载目录（精品发布习惯）。
- 设环境变量 **`YUNJI_TRACE_LOCAL=1`** 时可恢复双写 exe 同目录 —— 真机排查首跑问题时让用户设上，
  再到 exe 同目录拿日志（无需翻 %TEMP%）。
- `crash.log` 仅在未捕获异常时生成，留 exe 同目录（部署目录）作为真崩溃取证，正常流程不出现。

## 六、踩坑铁律（避免再踩）

1. **「Popen 拉起的普通窗口」无前台权** → 显示用短暂置顶，别信 `AllowSetForegroundWindow`/`AttachThreadInput` 前台锁 hack（真机无效）。
2. **删除自身必须靠独立 entry 进程 `os.remove`**，别用 `MoveFileEx`（需管理员）、别「等退出才删」（app 运行期永不触发）、别把条件复杂化（会永不删）、别运行中 rename（触发杀软）。
3. **进程清理必须递归进程树**，别关键字匹配 + 别只杀父进程（漏杀孙进程）。
4. **窗口居中由代码强制 `move`**，别交给 OS 窗口记忆（跨分辨率/小屏会落屏外，造成「isVisible=True 但看不到」假象）。
5. **后台构建在沙箱不持久** → 一律前台阻塞跑（`build-version.py` 带长超时）。
6. **绝不在 `/tmp`（映射到 `D:\Temp`）跑 exe 冒烟测试** —— 曾把约 39GB 部署目录写入 D 盘、残留清理进程占满 I/O 致整机卡顿。改 `E:\_smoke\` 且测完即清。

## 七、真机验证方法

1. 全新目录（如 `D:\freshtest`）删掉旧的 `云集智能音乐创意台\` 文件夹；
2. 把便携版本号 exe 放进去双击；
3. 预期：① 首跑主窗口立即置顶弹出（2s 后变普通窗口）；② 便携 exe 立即消失，仅留 `云集智能音乐创意台\`（入口 + ver 归档）；
4. 排查时设 `YUNJI_TRACE_LOCAL=1` 重跑，看 exe 同目录 `yunji_launch_trace.log` 末尾：
   `window shown (topmost-2s)` 与 `entry: deleted original ...`。
