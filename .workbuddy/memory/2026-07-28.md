## 下载过程闪退排查与修复

### 用户反馈
"上个版本除了进度条不显示，还有下载过程导致闪退，不知新版本（已修进度条的 v2026.07.28.0041）是否也解决。"

### 排查结论
- 项目**已有两层 Python 异常防护**：`SafeApplication.notify`（main.py ~8696，捕获事件循环/信号槽回调里的未处理 Python 异常 → 写 `crash_log.txt` 并继续运行，防闪退）+ `sys.excepthook = _global_excepthook`（~8723，主线程未捕获异常写日志）。**Python 层异常（含"wrapped C/C++ object has been deleted"的 RuntimeError）都会被兜住，不会让进程消失。**
- 用户描述的"闪退"（进程直接消失、无日志）必然是 **C++ 层段错误（segfault）**——它绕过 Python 防护，直接崩进程。
- **确定存在的 segfault 根因**：`closeEvent` 的 `_force_exit=True` 分支（托盘退出触发）只 `wait()` 了 `self.monitor`，**完全没等待 `model_download_thread` / `model_delete_thread` / `model_verify_thread` / `init_worker`**。用户在下载/删除/验证进行中触发退出 → 主窗口 C++ 对象被销毁，但后台线程仍在跑、继续经信号回调主线程 → 与 Qt 对象析构竞态 → 段错误闪退。**这极可能就是"下载过程导致闪退"的真实场景（下载中点了退出/托盘退出）。**
- 下载进行中（窗口开着、未退出）的静态审查：所有 UI 更新都经信号（跨线程 QueuedConnection），无跨线程直接访问 Qt 对象；信号连到的 widget 常驻不销毁；Qt 会在 receiver 析构时自动断开连接。**未发现确定的 segfault 点。**

### 修复（main.py `closeEvent` `_force_exit` 分支）
在 `self.monitor.stop()` 之前，插入对所有后台线程的安全停止+等待：
```python
for _t in (model_download_thread, model_delete_thread, model_verify_thread, init_worker):
    if _t is not None and _t.isRunning():
        if callable(getattr(_t,'stop',None)): _t.stop()   # 模型线程会 terminate 子进程
        _t.quit(); _t.wait(3000)                        # 同步等到 run() 返回再销毁窗口
```
效果：closeEvent 返回前 worker 已停止 emit，事件循环关闭时不再有该 worker 的排队信号 → 消除退出期段错误。
附加正确性：退出时被 stop 的 worker 不会 emit `download_finished`，故 `_on_download_finished` 里的 `QMessageBox.warning(self,...)` 不会在退出期弹窗（避免访问已死 parent）。

## 模型下载进度条"全程0%" 真正根因 + 结构化进度根治

### 用户连续多版反馈"下载进度条全程0%，但日志能显示进度"
此前 v2233/v0041 我反复在 main.py 侧靠正则解析 huggingface_tqdm 文本 + 磁盘兜底猜测目录，均失败。本次定位**真正的两个根因**：

1. **路径不一致 → 磁盘兜底测错目录 → 返回 None → 进度恒 0%**。
   - `main.py._fs_get_checkpoints_dir(base_dir)` 复刻的目录 = `<deploy_root>/data/models`；
   - 下载器 `model_downloader.get_checkpoints_dir()` **优先用 `config_manager.get_checkpoints_dir()`**（可能落在别处），fallback 才是 `app/data/models`。
   - 两者不一致 → `_compute_target_and_estimate` 把 `_target_dir` 设成"没在增长"的目录 → `_dir_progress` 的 `not os.path.isdir(self._target_dir)` 命中 → 返回 None。
2. **huggingface_hub 在管道（非 tty）模式默认禁用 tqdm 进度条** → 日志里根本不出现 `45%` 那种行 → 正则 `_PROGRESS_PCT_RE` 匹配不到 → 进度恒 0%。（用户看到的"日志有进度"多是 `print("Downloading main model from...")` / `Destination:` 这类静态行，非实时 `%`。）

### 根治方案（不再依赖脆弱文本解析）
**让下载器自己吐结构化进度行**，GUI 用固定正则 100% 命中（`acestep/model_downloader.py` + `main.py` 双端改）：
- 下载器新增：
  - `_make_hf_progress_reporter(repo_id)`：包 huggingface `snapshot_download(progress_callback=...)`，用 `list_repo_files` 拿文件总数，按「已完成文件数 + 当前文件%」聚合整体进度，打印 `[DLPROGRESS] <pct>`（`flush=True`）。兼容新旧 `ProgressInfo` 两种回调签名；任何异常都吞掉，**绝不阻断下载**。
  - `_start_disk_progress_monitor(local_dir, est)`：子进程内守护线程，按**子进程自己解析出的 `local_dir`**（路径 100% 正确）轮询 `_get_directory_size` 打印 `[DLPROGRESS]`，用于 modelscope（无结构化回调）及 HF 兜底。
  - `_estimate_repo_size`：已知仓库近似大小（主模型 18GB）作磁盘估算分母，未知回退 15GB。
  - HF 路径：`progress_callback=reporter`（精确）+ 磁盘监控（兜底）**双路**；仅当 `inspect.signature` 确认 `snapshot_download` 支持 `progress_callback` 才传（老版本不支持则回退普通调用，防 TypeError 崩下载）。
  - modelscope 路径：仅磁盘监控（其 `snapshot_download` 不支持该参数，不强加）。
  - 两路都在 `local_dir.mkdir(...)` 之后打印 `[DLTARGET] <local_dir>`（下载器自己解析的真实写入目录）。
- `main.py` 下载线程：
  - 新增 `_DLPROGRESS_RE = r"\[DLPROGRESS\]\s*(\d{1,3}(?:\.\d+)?)"` 与 `_DLTARGET_RE = r"\[DLTARGET\]\s*(.+)"`。
  - `_parse_frame_progress` **优先级**：`[DLTARGET]` 设 `_target_dir`（覆盖 `_compute_target_and_estimate` 的猜测，消除路径不一致）→ `[DLPROGRESS]` 直接取 pct（最高优先级、绝不误判）→ 旧 `%` 正则 → 旧尺寸比正则。
  - 读取循环里 `[DLPROGRESS]`/`[DLTARGET]` 行**只喂进度条、不进用户日志**（避免刷屏）。
  - `_dir_progress` 加固：`_target_dir` 由 `[DLTARGET]` 正确设置后，预估大小缺失也回退 15GB 分母，保证磁盘兜底始终产出进度。
- 实测（沙箱模拟解析逻辑，用真实临时目录）：`_target_dir` 正确取自 `[DLTARGET]`；进度序列 `3→12→45→78→99` 单调递增非零；`45` 重复一次是 `%` 正则对同一条 tqdm 行也命中（单调性守卫使其无副作用）。
