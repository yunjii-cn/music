## 🐞 破坏性回归修复：version_manager ImportError 致模型管理/软件更新页点不动（v2026.07.29.0530）

### 现象

### 根因（我 07.29 加"打开模型目录"按钮时引入）

- **但 PyQt6 中 `QDesktopServices` 位于 `PyQt6.QtGui`，不在 QtCore**（已实测：从 QtCore import 报 `ImportError: cannot import name 'QDesktopServices'`）。
- 该 import 在模块顶层 → 整个 `version_manager` 模块加载即 ImportError → main.py 在 `_create_model_page`/`_create_version_page` 里延迟 `from version_manager import ...` 抛异常 → 两个页面（ModelManagerDialog / HybridVersionManagerDialog 都来自该模块）都建不出来 → 点导航按钮 `_switch_page` 内部异常被 Qt 异常处理器吞掉 → 表现为"点不动"。

- **PyQt6 模块归属**：`QUrl` 在 `PyQt6.QtCore`；`QDesktopServices` 在 `PyQt6.QtGui`。跨模块的符号不能混在一个 import 行。

### 软件版本下载 404 根因与修复（本批次关键发现）
- **根因（不是代码 bug）**：Gitee 仓库 `yunjii/music` 实际只有 `wheels`、`frontend` 两个 release，**没有任何版本号 exe 的 release**；`dev/app/versions.json` 里几乎所有 `download_url` 为空，仅 2 条还是过期地址（实测均 404）。即这些 exe **从未被上传到 Gitee/GitHub release**，下载自然 404。Gitee API `repos/yunjii/music/releases` 实测确认只有那两个 release。
- **代码侧真实缺陷**：① 原 `_ExeFetchWorker.run()` 先 join 远程源（最长 20s）才 emit，离线/慢网时版本页卡"加载中"、非秒开；② 中文文件名拼进 download_url 未做 percent-encoding，`urlopen` 会失败；③ 内置兜底 emit 时 `winner="builtin"` 导致 download_tpl 取不到、下载按钮无 URL。
- **修复（version_manager.py）**：
  1. `_ExeFetchWorker.run()` 改为**先立即 emit 内置 versions.json（winner="gitee"）实现秒开**，再后台竞速拉远程、拿到后二次 emit 覆盖。
  2. `_on_exe_data_ready` 与 `_start_inline_download` 的 download_url 拼装均对中文文件名 `quote()` 编码；下载前 `do_download` 内再加 `urlparse+quote(path)` 兜底确保路径编码。
  3. 下载 URL 由 `version+name` 确定性拼 Gitee release 模板 `https://gitee.com/yunjii/music/releases/download/v{version}/{filename}`，上传后自动可下载，无需 json 维护 download_url。
- **上传补齐（解决 404 的本体）**：新增 `dev/app/upload_releases.py`（Gitee token 读 `.gitee_token`，实测 HTTP 200 有效），把 `dist/*.exe` 按 `v{version}` tag 创建 Gitee release 并上传资产。运行 `python upload_releases.py [--only v1,v2] [--dry-run]`。token 无上传范围限制（已成功建 release+传 50MB+ 资产）。
- ⚠️ 上传是**必做项**：仅改代码、不上传 exe 到 Gitee release，下载仍 404。每次 `_driver_build.py` 产出新版本后，需对**新版本**补跑 `upload_releases.py --only <新版本>` 才能下载。
- 验证手段：`curl -s -o /dev/null -w "%{http_code}" "https://gitee.com/yunjii/music/releases/download/v<ver>/<quote(中文名)>"` 应返回 200（上传成功后）。
- **最终构建 v2026.07.29.0702**（53.1MB）已打包含全部修复；已实测 `curl -sL` 从 Gitee 拉取该版本得到完整 55636516 字节（302→foruda 签名URL→200），下载链路端到端打通。0702 已单独上传成功；历史 23 个版本由 `upload_releases.py` 后台批量上传（每个~53MB，约1-2分钟/个）。
- ⚠️ 注意：Gitee release 下载 URL 会 302 跳转到 `foruda.gitee.com` 签名地址，`urllib`/`requests` 跟重定向即拿到真实文件；旧版 exe 客户端 `urlopen` 默认跟随重定向，无需改。

## 开发动态（git 提交历史）静态化 — 内置 git_commits.json 秒开 + 远程仅手动（v2026.07.29.0852）

### 用户需求（承接 0748）

### 对称性设计（最终落地）
「软件版本」(内置 `versions.json`) 与「开发动态」(内置 `git_commits.json`) 现在**完全一致**：打开页面只读 exe 内置静态文件（零网络零弹窗秒开）；只有点顶部「🌐 远程获取」按钮 (`_load_versions(force=True, auto_remote=True)`) 才联网。

### version_manager.py 改动

### 🔴 致命坑：GitHub release 资产名会静默丢弃所有非 ASCII（中文）字符
- 实测：上传资产名 `云集智能音乐创意台-v2026.07.29.0911.exe` → GitHub 存成 `-v2026.07.29.0911.exe`（中文前缀整个没了）；`测试中文name.exe` → `name.exe`。
- 与编码无关：`quote()` 编码正确、requests `params` 字典原生编码也正确，GitHub 字段本身把中文前缀吞掉。Gitee 则正常保留中文名。
- **解法（已落地）**：GitHub 资产名统一用 ASCII `yunji-music-v{version}.exe`；客户端对 `github_mirror`/`github` 源用此 ASCII 名拼 URL，对 `gitee` 源仍用中文原名。

### upload_releases.py 修正
- `gh_upload_asset` 改为：从 `filepath.name` 正则提取版本号 → `ascii_name = yunji-music-v{版本}.exe`；删除判定扩展到「匹配中文原名 / ascii_name / 以 `-v` 开头的坏资产」避免 422 与残留。
- `--github` 语义改为「**仅上传 GitHub**（不动 Gitee）」——避免清理后的 Gitee 配额再被旧版本占满；默认无 `--github` 仍只传 Gitee。

### version_manager.py 下载 URL 修正
- 新增 `_asset_filename_for_source(source_key, version, chinese_name)`：github 系源返回 `yunji-music-v{version}.exe`，gitee 返回中文原名。
