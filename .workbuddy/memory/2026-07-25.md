## 第二轮修复：部署超时杀进程 + 模型下载 No module named 'acestep'

### 现象（用户 02:13 日志）
- torch 2.7GB 慢速下约 46 分钟（日志 3 次 "Downloading torch"），被 **30 分钟(1800s) 硬超时强杀**（`_stream_powershell` 总耗时 > timeout 即 `proc.terminate()` 返回 -1），导致后续项目依赖/flash_attn 全没装。
- 之后却误报「环境已就绪，正在自动下载完整基础模型包」→ 下 main → `ModuleNotFoundError: No module named 'acestep'`。

### 根因 1：安装超时太短
`main.py:5996` 调 `_stream_powershell(..., timeout=1800)`。torch 2.7GB 在国内慢速网络实测 40+ 分钟 > 30 分钟，正常安装被误杀。
→ 修复：调用处 timeout 改 **5400**（90 分钟，留 2x 余量）；函数默认 `def _stream_powershell(..., timeout=5400)` 也同步抬高，避免将来漏传 timeout 复发。

### 根因 2：模型下载子进程缺 PYTHONPATH（真凶 `No module named 'acestep'`）
`main.py:642` 拉起模型下载用 `powershell -Command "cd '<app>'; <venv>/python -m acestep.model_downloader"`，**只 cd 没设 PYTHONPATH**。
- `run_gradio.ps1`/`run_server.ps1` 都显式 `$env:PYTHONPATH = "$project_root;..."` 才让 `acestep` 可导入。
- 关键机制：Python 3.11+ 引入 **`PYTHONSAFEPATH`**——它会让 `python -m` **不再把 cwd 加进 `sys.path`**。所以只靠 `cd` 的 `acestep` 导入必定失败；而显式 `PYTHONPATH` 不受 `PYTHONSAFEPATH` 影响，故 run 脚本能跑。
- `acestep/__init__.py` 确实存在（普通包，非命名空间），有 PYTHONPATH=app/ 即可 `import acestep`。
→ 修复：模型下载（642）与模型删除（767）两处 `-Command` 都注入 `$env:PYTHONPATH = '{self.base_dir}' + [System.IO.Path]::PathSeparator + $env:PYTHONPATH;`（与 run 脚本一致）。用 replace_all 两处同改。

### 根因 3：自动下载在环境未就绪时误触发 + 谎报"环境已就绪"
`main.py:3384` 结尾块只判 `_auto_deploy_initiated` 标志，**没看 `environment_installed`**。超时那次强杀没重置该标志 → 后续成功调用带着"已初始化"标志去下模型，下到半残环境里报错；且无论环境是否真装好都打「环境已就绪」。
→ 修复：结尾块改为 `if environment_installed:` 才自动下载并打"环境已就绪"；否则打「[警告] 环境未完全就绪，已跳过自动下载」。**不再谎报**。

- CArchive 校验：包内 main.py 含 `timeout=5400`（调用处+函数默认）、`$env:PYTHONPATH = '{self.base_dir}'`（出现 2 次=下载+删除）、`环境未完全就绪，已跳过自动下载`；`timeout=1800` 残留 = False。

## 第三轮修复：自动化部署维护「闪退」（进程无日志直接消失）

### 现象
用户用 `v2026.07.25.0246.exe` 跑初始化后的「自动化部署维护」（一键部署维护全流程），部署维护进行中/完成时进程直接消失，无任何 traceback。

### 根因（此前被 flash_attn 卡死完全掩盖，修好卡死后首次暴露）
`v0246` 在 `_enable_buttons` 里加了 `if environment_installed:` 判断（第 54 行的"修复"），但 `environment_installed` 是**部署线程 `_deploy_maintenance_thread` 的局部变量**，在 `_enable_buttons`（主线程槽）作用域里**根本不存在** → NameError。
- 之前一直卡在 flash_attn（`_stream_powershell` 永不返回），部署线程从没走到 `finally: enable_buttons_signal.emit()` → `_enable_buttons` 的完成逻辑（含该 NameError）**从未被执行**，所以不崩。
- 修好 flash_attn 卡死后，流程跑通到 `finally` → `enable_buttons_signal.emit()`（跨线程 QueuedConnection）→ 主线程事件循环执行 `_enable_buttons` → 命中 NameError。

**关键验证（沙箱 PyQt6 + offscreen 实测）**：PyQt6 中，跨线程信号触发的槽里抛未捕获异常会**直接终止进程（exit code 127），且不打印任何 Python traceback**——这正是"闪退无日志"的机理。普通 Python 异常被 PyQt 在 C++ 层 abort，无机会打印。

### 修复（main.py）
1. 部署线程在 `environment_installed` 确定后写入实例属性 `self._env_installed_in_last_deploy`（5984 后、rc==0 的 6017 后两处）；`_enable_buttons` 改用 `getattr(self, '_env_installed_in_last_deploy', False)` 读取，彻底消除 NameError。
2. 新增 `_safe_enable_buttons()` 包装，整体 try/except 吞掉任何异常（异常打到日志+print，不再闪退）；`enable_buttons_signal.connect(self._safe_enable_buttons)` 改走该包装。双保险，杜绝今后任何未捕获槽异常再静默闪退。

## 第四轮：彻底根治跨线程 GUI 闪退 + 全量审计

用户要求"彻底根治 + 顺带看隐患与可完善项"。本轮回溯了**全部后台线程对 widget 的直接调用**，并实测验证了 PyQt6 静默崩溃的真正机理。

### 全量审计结论（跨线程 GUI 访问点）
后台线程（threading.Thread / QThread）里调用 GUI 方法，只有两类会原生崩溃：
- **跨线程信号槽里抛未捕获 Python 异常**：PyQt6 在 C++ 层直接 abort，exit 127 无 traceback（`notify` 重写兜不住，详见下）。
- **后台线程直接调 widget 方法**（不走信号）：同样可能原生崩溃。

逐一排查后，确认**活的后台直碰 widget 只有两处**：
1. `_start_project_services`（后台线程 3044）内 6 处直接 `self._enable_buttons()`（3085/3093/3174/3235/3245/3371）→ setEnabled/setVisible/_deploy_progress_stop 全在主线程对象上操作。
2. `_install`（后台线程 5356）的 `finally` 里 `self.btn_one_click_deploy.setEnabled(True)`（5353）。

其余后台路径均安全或无害：
- `_do_check`/`read_api_output`/`ServiceProcess.run`/`start_service_thread`/`delayed_start`/`InitWorker` 槽/`_update_deploy_step` 槽/模型下载槽：只发信号(`_log`/`output_received`/`deploy_step_signal` 等)或 `_log`(信号安全)，不直碰 widget。
- `_update_bottom_bar` 是**空函数(pass)**——3042、5354 调它其实不碰 widget，非崩溃源（已澄清）。
- `_open_url_in_browser` 只 `_log`+`webbrowser`，无 widget 操作。
- `_check_and_load_system_info`/`_start_initialization_in_log`（含 `log_output.append`）**全文件无任何调用方**（死代码），当前不触发。

### 关键实测（推翻了"notify 重写能根治"的假设）
沙箱 PyQt6 + offscreen 两套实测：
- 跨线程 QueuedConnection 槽**内部有 try/except**（即 `_safe_enable_buttons` 模式）→ 异常在 Python 层被拦，**进程存活(OK_EXIT)**。
- 跨线程 QueuedConnection 槽**无内部 try/except**，仅依赖 `SafeApplication.notify` 重写 → 进程**照样 exit 127 闪退**，"caught" 都没打印。
**结论**：真正能拦住跨线程槽异常的是「信号投遞 + 槽函数内部 try/except」；`QApplication.notify` 重写对 queued 槽无效（PyQt6 C++ 层 abort 在 notify 之前）。notify 重写只对**同线程事件处理器/直连槽**异常有效，仍保留作补充网（无害、能写 crash_log）。

### 修复（main.py）
1. `_start_project_services` 6 处 `self._enable_buttons()` → `self.enable_buttons_signal.emit()`（16 空格版 replace_all，不会误伤 `_safe_enable_buttons` 内 12 空格那处）。投遞到主线程经 `_safe_enable_buttons`(内部 try/except) → 安全。
2. `_install` 的 `finally`：`setEnabled(True)`+`_update_bottom_bar()` → `self.enable_buttons_signal.emit()`（注释说明后台必须走信号）。
3. 全局防闪退安全网（补充层）：`class SafeApplication(QApplication)` 重写 `notify()` 捕获同线程事件/直连槽异常并写 `crash_log.txt`+stderr；`sys.excepthook = _global_excepthook` 兜底主线程未捕获异常；`_write_crash_log` 写 exe 同目录 `crash_log.txt`。`main()` 改用 `SafeApplication(sys.argv)`。注意：`QApplication` 在 177 行顶层已导入，子类定义在模块加载期可解析（已验证）。

- CArchive 校验：`enable_buttons_signal.emit()` 共 8 处（6+1 本次改 + 6179 既有 1 处）全部线程安全；`self._enable_buttons()` 仅剩 1 处（在 `_safe_enable_buttons` 内）；`btn_one_click_deploy.setEnabled(True)` 仅剩 1 处（在 `_enable_buttons` 主线程内，合法）；`SafeApplication`/`_global_excepthook`/`_write_crash_log`/`notify` 重写均命中；`_install` finally 已无直碰 widget。

## 第五轮：flash_attn 崩溃导致"环境未就绪"+模型下不了（根因修复）

### 现象（用户 06:22 部署日志 + 23:22 检测）
- 06:22 跑一键部署：torch 2.9.0 + transformers/diffusers/gradio/peft/accelerate 等**全部装成功**（06:31:49 整屏 `Installed`）。
- 但最后 `flash_attn` 下载步骤 `curl.exe` 抛 `NativeCommandError`（`install-env.ps1:271` 显示 `2>$n` 而非 `2>$null`）→ 未被 `try/catch` 拦住 → 整脚本返回码 1。
- 结果：main.py 判"环境安装失败" → `environment_installed=False` → 模型自动下载被跳过；23:22 单独"检测环境状态"也显示 python_deps 未就绪。

### 根因（两个独立 bug 叠加）
1. **flash_attn 崩溃（致命）**：脚本开头 `$ErrorActionPreference="Stop"` 下，native 命令 curl 往 stderr 写的进度条在无效应重定向时会被 PowerShell 当致命 `NativeCommandError` 抛出。flash_attn 整段下载+安装此前**无任何 try/catch 包裹**，一个可选优化包下载失败就一票否决整个部署。
2. **venv 路径发现脆弱（23:22 抱怨的"检测也显示未就绪"）**：`find_venv_python()` 候选路径若因 relocate 后 `base_dir` 偏差全部 miss，返回默认不存在路径 → `_check_deploy_env` 的 `os.path.exists(venv_python)`=False → `venv` 与 `python_deps` 双判失败（即便包已装好）。
