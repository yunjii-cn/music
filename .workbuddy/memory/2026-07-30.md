## 软件更新栏「打开即远程拉取」Bug 修复（用户复核视频创意站后反馈）

### 用户原话
"打开软件更新栏目会有一连串一闪而过的运行窗口；参考视频创意站怎么做到没弹窗的；我明明说直接读本地静态历史版本列表、打包exe应包含此文件，为何还要远程拉取？"

### 根因（已定位并修复）
- `version_manager.py` 的 `_on_exe_data_ready`（原 1016）在**打开页面时无条件**调用 `self._fetch_release_assets(winner_source, all_versions)`，去打 GitHub/Gitee Releases API。
- 但版本列表本身已由 `_get_builtin_versions()` 从 **exe 内置 `versions.json`**（`sys._MEIPASS/versions.json`，构建时 `--add-data` 打入）读取，且每张版本卡的 `download_url` 早在合并阶段用 `download_url_tpl` 模板算出（已验证三源 200）。所以这次打开即发的网络请求纯属多余，且违背"只在点远程获取才拉取"的指令。
- 参考项目（视频创意站）`main.py:10648` 注释明确："无缓存时只从本地 versions.json 加载，不自动发起远程请求"——即本地优先、远程仅在点"检查更新"时触发。本次改动即对齐该行为。

### 修复
- `_load_exe_versions` 记录 `self._exe_did_remote = auto_remote`。
- `_on_exe_data_ready` 改为 `if winner_source and getattr(self, '_exe_did_remote', False): self._fetch_release_assets(...)` —— 仅显式远程获取（点「🌐 远程获取」，`auto_remote=True`）才打 Releases API 拉真实资产链接；打开页面零网络。
- `py_compile` 通过；`_fetch_release_assets` 仅余 1 处受守卫的调用点（line 1021）。
- 注意：version_manager.py 是 `--add-data` 打进 exe 的，**需重新 build-version.py 打包才对产物生效**。

### 关于"闪窗"的代码层结论（已追完更新页打开路径每一个函数，确定）
- 用户确认：点「软件更新」标签那一刻闪、**黑底白字 CMD 窗口** → 典型"漏 CREATE_NO_WINDOW 的 console 子进程"。但更新页打开路径经逐函数追查，**零 subprocess**：
  - `_get_current_exe_version`(709)：文件名正则 + `os.path.getsize`，无 git/无 subprocess。
  - `HybridVersionManagerDialog.__init__`(410)：`_setup_ui` + 读 `version_history.json` + 延迟 timer，无 subprocess。
  - `_check_git_repo`(453)：仅向上遍历目录判断 `.git` 是否存在，零 subprocess。
  - worker 全程 `urlopen`；本次又把打开即发的 `_fetch_release_assets` 关了。
- 全仓 `subprocess.Popen/run/call/check_output` 均被 main.py(45-93)+`pyi_rth_subprocess.py` 双重 CREATE_NO_WINDOW 补丁覆盖；`QProcess` 仅 import 未使用；无 `os.popen/os.system/ShellExecute/ctypes CreateProcess`。
- **铁证**：version_manager.py:423 注释"避免打开页面即触发远程拉取/弹窗"——旧版确实打开更新页就弹窗+远程，后来源码已修。用户所见闪窗 = **正在跑的构建是旧版**（源码已干净）。
- 结论：当前源码更新页不可能闪 CMD 窗口；修复方式是**用当前源码重新 build-version.py 打包**。需提醒用户：若重打后仍闪，则窗口来自启动期子系统（模型/嵌入式python下载）而非更新页，届时再追。

## 根治闪窗：打开更新页改纯同步静态列表（v2026.07.30.0605）

### 触发
用户实测 v2026.07.30.0526 仍"每次打开软件更新页弹一连串运行窗口"，明确要求"改用直接显示静态列表，参考视频创意站"。

### 根因再定位
- 上一轮只关了 `_fetch_release_assets`（本就 urlopen 不产窗口），未触及真正架构问题：打开页仍**启动 _ExeFetchWorker（QThread）异步加载**。
- 另发现 `_get_local_exe_versions` 方法**定义丢失**——其方法体（832-879，glob+stat 扫本地 exe）被错误地卡在 `_normalize_commit` 的 `return` 之后成为**不可达死代码**；worker 调用时 AttributeError → except 兜底。
- 视频创意站做法（main.py:10880-10962 `_load_all_versions_fallback`）：**纯同步** `json.load(versions.json)` + glob 扫 exe + 渲染，零线程零网络零子进程。

### 根治改造（version_manager.py，三处）
1. **`_load_exe_versions`（927）改同步**：`auto_remote=False`（打开页）时不启动 worker，直接同步 `_get_current_exe_version()` + `_get_builtin_versions()` + `_get_local_exe_versions()` → `_on_exe_data_ready()` 渲染；仅 `auto_remote=True`（点远程获取）才启 worker。
2. **`_load_git_versions`（1715）改同步**：同理，`auto_remote=False` 时同步读 `git_commits.json` → `_on_git_data_ready`。
3. **修复 `_get_local_exe_versions` 方法丢失**：把 832-879 死代码从 `_normalize_commit` 移出，独立成 `def _get_local_exe_versions(self):`（glob+stat，不 spawn）。

### 效果
打开更新页执行链变为：文件名正则 → json.load(内置 versions.json) → glob+stat 扫本地 exe → Qt 渲染。**全同步、零线程、零网络、零子进程**——与视频创意站一致，彻底消除闪窗可能。
- py_compile 通过；exe 内部 CArchiveReader 校验：`_get_local_exe_versions` 定义✓、`if not auto_remote:`✓、同步直调 `_on_exe_data_ready`/`_on_git_data_ready`✓、`_normalize_commit` 不含死代码（`local_versions={}` 仅 1 处）✓。
