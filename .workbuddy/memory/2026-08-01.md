# 2026-08-01 工作日志

## 首跑「删除自身」终极修复（exe v2026.08.01.0019）
- **现象**：2359 版首跑能显示启动器，但不删除原始便携 exe。根因：2359 用 `MoveFileEx(MOVEFILE_DELAY_UNTIL_REBOOT)` 重启删除，**需管理员权限**，非管理员下静默失败（`_safe_delete` 才是 `os.remove` 带重试、无需管理员）。另：当前首跑分支 `_ensure_entry_current` 在 `ver/` 为空时返回 None，入口从未生成（隐患）。
- **方案（双保险，恢复 git 历史 f7d9105 语义 + 防黑屏兜底）**：
  1. **首选（恢复历史 spawn 机制）**：首跑 spawn 固定名入口 entry 带 `--cleanup=<原始便携exe>`；entry 显示后 `_safe_delete(cleanup_target)` 立即删（os.remove，无需管理员）。加**看门狗** `_wait_entry_ready`：spawn 后等 ~4s 确认 entry 存活才 `os._exit(0)`；若被杀软杀掉则 supervisor 自己 fall-through 显示（保显示不黑屏）。
  2. **兜底（杀软拦了 spawn 也能删）**：首跑时把原始 exe 绝对路径写到 `部署目录/.cleanup_pending`；下次以已部署态启动时（文件已不在运行）读它 `os.remove`（无需管理员、不触发杀软）。另在 fallback 显示后派生 `--self-delete-helper` 助手（同 exe，DETACHED）：等 supervisor 退出后删原始 exe——显示后才派生，被杀只损「立即删」、不损显示；被杀则靠 .cleanup_pending 下次启动兜底。
- **入口创建修正**：首跑分支恢复「生成 entry（_ensure_entry_current）+ 复制自身进 ver/」（`_find_newest_versioned_exe` 把 current_exe 也纳入候选，故 entry 硬链到便携 exe；删便携后硬链仍保数据，但额外复制 ver/ 副本更稳）。
- **结论**：无论杀软是否拦 spawn，都能「既显示又删除自身」。最坏情况（拦 entry 又拦 helper）= 原始 exe 在用户**下次启动**时被 .cleanup_pending 清理（延迟一启，但必删、无需管理员）。
- **git 历史核对**：f7d9105 的删除机制本就是 spawn entry + `--cleanup` + `os.remove`（无需管理员），并非我之前怀疑的「被我改写坏」；首跑 spawn 模型与两天前一致。1507 首跑不显示是**真机杀软在 bootloader 阶段杀了被 spawn 的 entry**（手动双击 entry 能跑佐证），非代码回归。
