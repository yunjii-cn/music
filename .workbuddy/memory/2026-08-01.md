## 首跑「删除自身」终极修复（exe v2026.08.01.0019）
- **现象**：2359 版首跑能显示启动器，但不删除原始便携 exe。根因：2359 用 `MoveFileEx(MOVEFILE_DELAY_UNTIL_REBOOT)` 重启删除，**需管理员权限**，非管理员下静默失败（`_safe_delete` 才是 `os.remove` 带重试、无需管理员）。另：当前首跑分支 `_ensure_entry_current` 在 `ver/` 为空时返回 None，入口从未生成（隐患）。
- **方案（双保险，恢复 git 历史 f7d9105 语义 + 防黑屏兜底）**：
  1. **首选（恢复历史 spawn 机制）**：首跑 spawn 固定名入口 entry 带 `--cleanup=<原始便携exe>`；entry 显示后 `_safe_delete(cleanup_target)` 立即删（os.remove，无需管理员）。加**看门狗** `_wait_entry_ready`：spawn 后等 ~4s 确认 entry 存活才 `os._exit(0)`；若被杀软杀掉则 supervisor 自己 fall-through 显示（保显示不黑屏）。
  2. **兜底（杀软拦了 spawn 也能删）**：首跑时把原始 exe 绝对路径写到 `部署目录/.cleanup_pending`；下次以已部署态启动时（文件已不在运行）读它 `os.remove`（无需管理员、不触发杀软）。另在 fallback 显示后派生 `--self-delete-helper` 助手（同 exe，DETACHED）：等 supervisor 退出后删原始 exe——显示后才派生，被杀只损「立即删」、不损显示；被杀则靠 .cleanup_pending 下次启动兜底。
- **入口创建修正**：首跑分支恢复「生成 entry（_ensure_entry_current）+ 复制自身进 ver/」（`_find_newest_versioned_exe` 把 current_exe 也纳入候选，故 entry 硬链到便携 exe；删便携后硬链仍保数据，但额外复制 ver/ 副本更稳）。
- **结论**：无论杀软是否拦 spawn，都能「既显示又删除自身」。最坏情况（拦 entry 又拦 helper）= 原始 exe 在用户**下次启动**时被 .cleanup_pending 清理（延迟一启，但必删、无需管理员）。
- **git 历史核对**：f7d9105 的删除机制本就是 spawn entry + `--cleanup` + `os.remove`（无需管理员），并非我之前怀疑的「被我改写坏」；首跑 spawn 模型与两天前一致。1507 首跑不显示是**真机杀软在 bootloader 阶段杀了被 spawn 的 entry**（手动双击 entry 能跑佐证），非代码回归。
- **构建**：v2026.08.01.0019.exe（53.1MB），dist/ + dev/ver/ + build/...0019/，git 提交推送双远程。

## 0447：修复「托盘退出后进程残留」（exe v2026.08.01.0447）
- **现象**：每次从系统托盘「退出」，仍有进程残留（主要是 powershell 服务脚本拉起的 node/python 子进程：vite 前端、ACE-Step API、gradio 等）。
- **根因**：① `_exit_all` 的进程清理是脆弱的关键字扫描——`psutil.process_iter` 仅匹配 cmdline 含 `acestep`/`qinglong`，而 ace-step-ui 目录带连字符、`acestep` 子串根本不匹配 → 前端 vite 永远漏杀；② `ServiceProcess.terminate()`（及 `_stop_service`）只 `self.process.terminate()` 杀 **powershell 父进程**，其 node/python 子进程（孙进程）不会被 SIGTERM 连带杀死 → 残留；③ `api_process.kill()` 同理只杀父。
- **修复（main.py，精确递归进程树清理）**：
  1. 新增模块级 `_kill_process_tree(proc)`：对 psutil.Process/subprocess.Popen 先优雅 `terminate` 整棵子孙树、超时 3s 再 `kill` 强杀（接受 psutil.Process 或 Popen，无 psutil 时退化为 Popen terminate/kill）。
  2. 新增 `_kill_child_processes()`：退出时遍历 `psutil.Process(os.getpid()).children(recursive=False)`，对名字∈{python,node,powershell,pwsh} 的直接子进程调用 `_kill_process_tree` 杀整棵子树。**只杀服务型进程、按进程树归属，绝误杀本启动器或升级时拉起的新版 exe**（其名非上述几类），故自更新流程不受影响。
  3. 用 `_kill_child_processes()` 替换 `_exit_all` 中原脆弱的关键字扫描块。
  4. `ServiceProcess.terminate()` 改为 `_kill_process_tree(self.process)`（连孙进程一并杀）——同时修了「停止单个服务」按钮也会残留 node/python 的隐患。
  5. `_stop_all_services` 中 `api_process.kill()` 改为 `_kill_process_tree(self.api_process)`。

## 0722：首跑「窗口可见但看不到」真正根因——Windows 前台锁（exe v2026.08.01.0722）
- **用户关键洞察**：「不就是正常启动 exe 吗？为啥第二次手动能正常启动、开发模式也能正常启动，第一次运行就无法正常启动」——要求研究首跑 vs 二次启动的区别。
- **三方路径对比**：首跑=versioned exe(supervisor) `Popen` 拉起 entry→supervisor `os._exit`→entry 跑 main 显示窗口（**失败**）；二次=双击 entry 由 Explorer 直接启动（**正常**）；开发=`python main.py` 由终端启动（**正常**）。entry 代码路径首跑/二次完全一致（都走 already-deployed 分支），唯一差异是 **entry 进程的启动方式**：首跑由 Popen 拉起，二次/开发由 Explorer/终端直接启动。
- **根因（Windows 前台锁）**：Popen 拉起的子进程**不继承前台权限**。entry 显示窗口时 `activateWindow()`→`SetForegroundWindow` 被 Windows 前台锁**静默拒绝** → 窗口 `isVisible()=True`（Qt 已 show）但停留在后台、用户看不到（只剩托盘）。Explorer/终端启动的进程自带前台权，故二次/开发正常。0509 轨迹铁证：`window shown | visible=True geom=(680,232,1200,988)` 且 15s 后 `force_show_window` 仍 visible=True，但用户就是看不到——典型「可见但非前台」。
- **修复（双保险）**：①launcher.py：supervisor `Popen([entry,...])` 后立即 `ctypes.windll.user32.AllowSetForegroundWindow(child.pid)`（Win32「父进程授予子进程前台权」标准机制）。②main.py：新增 `_force_foreground()` 用 `AttachThreadInput(绑当前前台线程输入队列)+SetForegroundWindow+BringWindowToTop+ShowWindow(SW_SHOW)` 突破前台锁（Win32 公认「子进程抢前台」做法），在 `_deferred_init` 显示后立即+500ms 双调用，`_force_show_window` 兜底也调用。
- **构建**：v2026.08.01.0722.exe（53.3MB），dist/ + dev/ver/，git 提交推送双远程。
- **验证待用户**：全新目录双击 0722 版便携 exe，预期首跑主窗口立即置顶显示（不再「只剩托盘」）。这是首次针对「首跑 vs 二次」差异的根因修复，非再凭猜测。
- **教训固化（写入 MEMORY.md）**：PyInstaller onefile「supervisor Popen 拉起 entry」模型下，entry 是 Popen 子进程、不继承前台权限，其窗口 activateWindow 会被 Windows 前台锁拒绝 → 必须 supervisor 侧 `AllowSetForegroundWindow(child_pid)` + entry 侧 `AttachThreadInput+SetForegroundWindow` 突破前台锁。这是「Popen 拉起的 GUI 子进程」通病，与「Explorer/终端直接启动」行为不同的根因。

## 0842：0722 的前台锁 hack 仍失败 → 改从根上消除差异（exe v2026.08.01.0842）
- **复核 0722 真机轨迹（D:\test，同一日志含 08:22 首跑 + 08:29 二次跑）**：两条路径 Qt 状态**完全一致**——都 `visible=True`、几何都是 `(680,232,1200,988)`。即窗口代码首跑/二次行为一致，窗口确实被 show。但用户首跑只看到托盘、二次看到窗口。且 0722 加的 centering 根本没生效（几何仍是 680,232），说明 `_force_foreground`/`AllowSetForegroundWindow` 那套**没起作用**。
- **关键澄清**：核对 git f7d9105 确认——f7d9105 首跑**也是** `Popen([entry,"--cleanup="+exe])`+`os._exit` 拉独立进程（与现架构相同），并非「直接在便携 exe 跑」。故「spawn 独立进程」不是 f7d9105 能显示、现在不能显示的区别；f7d9105 的「能首跑显示」是别的因素（或用户记忆偏差）。但「首跑=被 Popen 拉起的 entry（无前台权）、二次=Explorer 直接拉起（有前台权）」这个差异是客观存在的。

- **删除自身（首跑）**：`_self_relocate` not-already 分支设 `YUNJI_PORTABLE_EXE=<便携exe路径>` 并 return；`_run_supervisor` 末尾 main 成功跑完后 `Popen([sys.executable,"--self-delete-helper",pid,便携exe路径], CREATE_NO_WINDOW)` 派生助手——助手等便携 exe 进程退出后 `os.remove` 删便携 exe（entry 为硬链接保活数据，删名不影响运行进程）。仅在 main 跑完才删（崩溃则不删，保留便携 exe 可重试）；删除从独立子进程、退出后执行，与旧 `--cleanup` 等价（无需管理员、不触发杀软）。`.cleanup_pending` 仍作兜底。
